# 通信設計

[English](../PROTOCOL.md)

## リーダー

- USB VID:PID は f00d:1337。RetroFreakのカートリッジアダプターで、USB CDC ACM（仮想シリアル）として動作する。
- 製品情報の応答は build と product の2つの16ビット値。製品識別に使う値は build=10、product=4919。
- 通信は要求と応答の同期型。1つの転送路を1つのワーカーが専有し、要求の途中で別の要求を送らない。

## 転送路

| 転送路 | 用途 | 設定 |
|---|---|---|
| SerialTransport | Windows、およびシリアルとして見える環境 | 115200bps、8N1、読み取りタイムアウト3秒、書き込みタイムアウト5秒、DTRとRTSを有効、フロー制御なし。接続時に入力バッファを破棄する |
| UsbTransport | MiSTer（Linux）のUSB直接通信 | PyUSBとlibusbによるバルク転送。読み取りタイムアウト3秒、書き込みタイムアウト5秒 |

### 転送路の選択

1. ポートを明示した場合はシリアルを使う。
2. USB直接通信を明示した場合はUsbTransportを使う。
3. どちらも指定しない場合、VID:PIDが一致するシリアルポートを列挙する。2台以上見つかればエラー（ポート指定を要求）、1台ならそのポートを使う。
4. 見つからずLinuxならUsbTransportを使う。Windowsで見つからなければエラー。
- 列挙は無関係なシリアル機器を開かない。開くのは識別したリーダーだけで、失敗したら別の転送路へ黙って切り替えず、エラーを伝える。

### UsbTransportの初期化

- VID:PIDが一致する装置がちょうど1台であることを要求する。
- アクティブな設定の中から、代替設定0で、バルクIN・バルクOUTが1本ずつある単一のインターフェースを選ぶ。曖昧または存在しなければ停止する。代替設定や構成の変更はしない。
- データインターフェースがCDCデータクラスの場合、制御インターフェース（CDC ACM）がちょうど1つあることを要求する。このリーダーはCDC Unionディスクリプターを持たないため、この条件で対応づける。
- 必要ならカーネルドライバーを切り離してインターフェースを占有する。終了時に解放し、切り離したドライバーを戻す。
- CDC制御：SET_LINE_CODINGで115200bps、8N1を設定し、SET_CONTROL_LINE_STATEでDTRとRTSを有効にする（シリアルと同じ設定）。
- 読み取りはエンドポイントの最大パケット長の倍数で行い、余剰バイトを内部バッファに保持する。タイムアウトは空のバイト列として返し、シリアルと同じ契約にそろえる。
- libusbはPython標準の探索に加えLinuxの既存共有ライブラリーを探す。ネイティブライブラリーは同梱しない。

### USB入力回復

- 接続直後と、送受信が失敗した後の次の要求の前に、上限付きで入力エンドポイントを読み捨てる。正常時の読み出しごとに無条件で読み捨てることはしない。
- 上限：0.5秒、256 KiB、64回の読み取り。1回の読み取りは20ミリ秒のタイムアウトで、連続2回の空読みで静止とみなす。
- 上限に達した場合はエラーにして、利用者に再確認またはUSB再接続を促す。失敗した要求を自動再送しない。
- 結果（outcome、discarded_bytes、reads、duration_ms）を直近の回復情報として保持し、ログへ出す。破棄したデータの内容は記録しない。
- 静止は「その時点でエンドポイントが空」という観測であり、ファームウェアやUSBのストールが復旧した証明ではない。

## パケット

- 要求はリトルエンディアンの32ビット符号なし整数の列。`packet(w0, w1, ...)` で組み立てる。
- 応答ヘッダーは8バイト：status（32ビット）と length（32ビット）。正常は status=0。length は後続のペイロード長。

## 共通コマンド

| コマンド | 要求 | 応答 |
|---|---|---|
| 0x01 製品情報 | (1, 0, 4) | ヘッダー length=4、続いて build と product（各16ビット） |
| 0x06 カートリッジ状態 | (6, 0, 4) | ヘッダー length=4（length=0 の応答も受理して未挿入とする）、続く4バイトの先頭1バイトが状態コード |
| 0x04 モード | (4, 4, 0, 値) | 8バイト。内容は検査せず記録する |
| 0x05 確定 | (5, 0, 0) | 8バイト。内容は検査せず記録する |
| 接続初期化 | (4, 4, 0, 0) | 8バイト。0x05は送らない |
| 0x2F SFCモード | (0x2F, 8, 0, 0, 値) の5ワード | 8バイト。値は最後のワード |

- 04と05の応答は、受信量だけを確認して内容の意味を推測しない。生の応答は診断用に直近32件まで保持する。
- 04に渡す値0／1の意味は確定していないため、機種ごとに決めた開始・終了の手順どおりに送るだけにする（GBAの開始だけは値0）。

### カートリッジ状態コード

| 値 | 意味 |
|---|---|
| 0 | 未挿入（length=0 応答） |
| 1 | SFC |
| 2 | MD |
| 3 | FC/NES |
| 5 | GB/GBC |
| 6 | GBA |
| 7 | 対応済みの状態コードとして扱う（SMS相当、読み出し機能は持たない） |
| 8 | PCE |
| 254 | 複数のカートリッジが同時に挿入されている |
| 255 | 未挿入（リーダーが返す実際の値）。通信断や未知の状態とは区別する |

- 未挿入のスロットは、ヘッダー（status=0、length=4）に続くペイロード FFFFFFFF で返る。
- 複数スロットに挿入すると254が返り、片方を抜くと残りの機種の値へ戻る。
- 4など定義にない値は「別機種／未知の種別」として表示し、挿入と抜去のどちらにも扱わない。
- 状態は連続して同じ値が3回得られたときに確定とする。未知の値は抜去とみなさない。

## メモリ読み出し

1. 入力バッファの古いバイトを破棄する。
2. 要求 (コマンド, 8, サイズ, アドレス, サイズ) を送る。
3. 応答ヘッダー（status=0、length=サイズ）を確認する。
4. 状態要求 (6, 0, 4) を続けて送る（PCEだけは後述のとおり送らない）。
5. サイズ分のデータを受信する。
6. 末尾の状態応答を読み、期待した機種のコードであることを確認する。違えば「カートリッジが消えた／変わった」として停止する。

- アドレスはバイト単位、1回の読み出しは最大32 KiB（SFCは24ビットアドレスで1〜32768バイト）。
- 受信は、指定バイト数が揃うまで繰り返す。全体の期限は10秒で、各受信の合間に確認する。下位層はそれぞれのタイムアウトでブロックするため、10秒以内に必ず戻る保証ではない。

### 機種別のコマンド

| 機種 | 読み出し | 書き込み | 備考 |
|---|---|---|---|
| FC/NES | 0x11 CPU空間、0x13 PPU（CHR）空間 | 0x12 通常書き込み、0x15 下位レジスター書き込み | 通常書き込みの後、0x11で0x8000から8バイトのダミー読み出しを行う（下位レジスター書き込みでは行わない） |
| GB/GBC | 0x1B | 0x1C | ROM領域の読み出しと、限定したバンク制御のみ |
| GBA | 0x1F | なし | 最大32 KiB |
| MD | 0x0D | 0x0E | 書き込みは0xA130F1と0xA130FFのみ |
| PCE | 0x2D | 0x2E | 状態要求は読み出し中に挟まず、全データ受信後に独立して確認する。書き込みは0x1FF0〜0x1FFFのみ |
| SFC | 0x07 | 0x08 ROMマッピング | 24ビットアドレス。モード切替に0x2Fを併用。書き込みはSA-1・S-DD1・許可したCX4のROM用レジスターと値だけ（[SFC設計](SYSTEM_SFC.md)） |

### 書き込み（バンク制御）

1. 要求 (コマンド, 8, 1, アドレス, 1) を送る。
2. 準備ヘッダー（length=0）を確認する。
3. 値1バイトを送る。
4. 完了ヘッダー（length=0）を確認する。

- 公開する書き込み口は機種・基板ごとに許可するアドレスと値を厳密に絞り、セーブRAM・ID・フラッシュ書き換えの鍵などへは到達させない。汎用の書き込み口（FCの cpu_register_write、GBの gb_register 等）は、ROMバンクレジスターの範囲外のアドレス・値を拒否する。
- 低アドレス（0x6000〜0x7FFF等）のレジスターが必要な基板には、その基板専用の関数を用意し、許可するアドレスと値だけを通す。

## 機種ごとのモード

| 機種 | 開始 | 終了 |
|---|---|---|
| FC/NES | 04(1)、05、200ms待機 | 04(0)、05 |
| GB/GBC | 04(1)、05、200ms待機 | 04(0)、05 |
| GBA | 04(0)、05、200ms待機 | 04(0)、05 |
| MD | 04(1)、05、200ms待機 | 04(0)、05 |
| PCE | 04(1)、05、200ms待機（電圧は探索的に切り替えない） | 04(0)、05 |
| SFC | 04(1)、2F(1)、05、05、$00:C000から16 KiBを読む | 2F(0)、04(0)、05 |

## エラーの設計

- 通信エラーは操作名・コマンド・アドレス・段階（ヘッダー、ペイロード、状態応答）と、受信済み／必要バイト数を含む。例：
  `Truncated response: no bytes returned (timeout or end of stream) [GBA read command 0x1F address 0x008000 payload; 2/8 bytes received]`
- 送信失敗は要求したバイト数と「実送信量不明」を示す。全部届いたとも全く届かなかったとも断定しない。
- 空の応答はタイムアウトまたはストリーム終了を示すだけで、ケーブルの抜去とは断定しない。
- 読み取り・送信の例外は元の例外名とメッセージを含め、例外チェーンに元の例外を残す。
- 不正ヘッダーは status、length、期待length、処理名を示す。
- 部分応答、不正ヘッダー、送受信例外が起きたトランザクションは継続も自動再送もしない。未読データでフレーム境界が失われている可能性があるため、サービスがセッションを閉じ、利用者が再接続する。
- 詳細は画面に収まらない場合があり、MiSTerでは runtime/manager.log に記録する。

## 診断

- probe：製品情報とカートリッジ状態だけを確認する（ROMは読まない）。
- 通信トレース：アプリケーションが転送路へ渡した送信バイト列（hex）、要求長、実際の受信バイト列とバイト数、接続後の相対開始時刻、呼び出し所要時間、エラーをJSON Linesで記録する。USB入力回復の結果も含める。既存のトレースファイルは上書きしない。
- `diagnose-gb` は、書き込みやバンク切替を伴わないヘッダー読み出しだけを行う。`probe-pce` は方式の判定に必要なサンプルを読み、必要に応じて限定したバンク切替を行うが、全体読み出しや保存は行わない。
