# 取り込み・検証・保存の設計

[English](../CAPTURE_FLOW.md)

## サービス層の責務

- Service は、1つの転送路、候補、選択、保存先、検証済みファイルの確認を1つのワーカーで所有する。Qtや端末に依存しない。
- 主な操作は次のとおり。

| 操作 | 内容 |
|---|---|
| poll | 未接続なら転送路を開いて製品情報を取得。カートリッジ状態を取得し、安定したら識別して状態スナップショットを返す |
| select_profile | 現在の候補の中から1件を選ぶ。候補が消えていれば再確認を要求する |
| retry | 接続を閉じてキャッシュを捨て、最初から poll し直す |
| capture | 選択中の候補（または自動判定グループ）を読み出し、検証して保存する |
| existing | 選択中の候補に対応する保存済みROMを、全体ハッシュで検証して返す |
| prepare_game | MiSTer用。保存済みROMを再照合してMGLを作り、起動情報を返す |
| close | 転送路と状態を解放する |

- 状態スナップショット（PollState）は、リーダー状態、カートリッジ表示、取り込み可否、候補一覧、選択中の候補、保存済みか、選択待ちか、自動判定の候補数、保存先を持つ。画面はこれだけを描画する。
- poll・capture・prepare_game のいずれかで例外が起きたら、サービスは転送路を閉じて例外を伝える。画面側は利用者の明示的な再接続を待つ。

## 挿入判定

- 同じカートリッジ状態が3回連続で得られるまで「安定待ち」と表示し、識別しない。値が変わるたびに候補と選択を破棄する。
- 未挿入（0または255）、複数挿入（254）、対象外の種別は、それぞれ別のメッセージで停止する。
- 同じ挿入のまま繰り返し識別しない。抜き差し・再接続・再試行で識別し直す。

## 機種別の識別

| 機種 | 識別の方法 | 取り込み前に確定するもの |
|---|---|---|
| FC/NES | 初期状態のPRGから先頭1 KiB、末尾1 KiB等の部分ハッシュを取り、DBの部分ハッシュ索引と照合して候補を作る（書き込み・バンク切替なし） | 候補のみ。タイトルは全体ハッシュ照合後に確定 |
| GB/GBC | ヘッダー（0x100から80バイト）を複数回読み、ロゴ・チェックサム・型・容量コードを検証 | ヘッダー上のタイトル、MBC、容量、GB／GBC区分 |
| GBA | 先頭2 KiBを独立して2回読み、固定値0x96とヘッダーチェックサムを検証 | タイトル、ゲームコード、版。容量は未確定 |
| MD | 0x100〜0x1FFを読み、SEGA識別子とROM範囲を解析 | タイトル、シリアル、読み出し方式、容量の候補 |
| PCE | 方式を判定し、一度ROM全体を読んでDBと全体ハッシュ照合 | 正式名、容量、データ順、PCE／SGX区分 |
| SFC | $00:FFB0の48バイトを複数回読み、チェックサム・マップ・容量コードを検証 | タイトル、方式、チップ、容量の上限候補 |

## 候補の選択

- 候補が1件：自動的に選ぶ。
- 候補が複数で、すべて読み出し対応済み、かつ mapper／submapper／PRG容量／CHR容量が同一（Mapper 206を除く）：手動選択せずに進める「自動判定グループ」とする。読み出し後の PRG・CHR・全体のSHA-1がちょうど1件の候補に一致した場合だけ、そのタイトルで保存する。
- それ以外の複数候補：利用者が選ぶ。未対応の候補が1件でも混ざればこの扱い。
- 候補の対応可否は、候補ごとに理由つきで示す。未対応の候補を選ぶと取り込みを無効にし、理由を表示する。
- 候補の一覧表示は「リーダーが対応している」という意味であり、タイトル・版が実物と一致する保証ではない。部分ハッシュは別タイトルや別版でも一致し得るため、全体ハッシュが一致するまでタイトルと版は未確定として扱う。選んだタイトルの全体ハッシュに一致した場合だけ保存する。

## 取り込み（capture）の手順

1. 選択済みで対応可能な候補（または自動判定グループ）であることを確認する。
2. 直前にカートリッジを再識別し、選択時の候補と一致することを確認する。変わっていれば停止する。
3. 独立した2回の全ROM読み出しを、機種ごとの手順で行う。進捗は「Read 1/2」「Read 2/2」の段階で通知する。
4. 2回の一致、ヘッダー、機種ごとの条件を確認する。
5. DBの全体ハッシュで照合する。不一致・未収録・SHA-256不一致は保存せず停止する。
6. 保存先を作り、検証済みデータを保存する。
7. 保存したファイルを読み直し、DBに照らして再検証する。
8. 結果として保存パスと、新規作成か既存再利用かを返す。
- 終了処理（モードを元に戻す）は、成功・失敗・中止のどれでも試みる。
- 中止は、安全な区切り（確認点）で行う。保存の書き込みを始めた後は、その処理の完了を優先する。保存前に中止した場合は新規ROMを保存しない。

### 検証の層

「独立」は、キャッシュや1回目のデータを流用せず、全範囲をもう一度取得することを指す。USBの再接続、電源断、すべての内部状態のハードウェアリセットは保証しない。

| 機種 | 2回目の開始状態 |
|---|---|
| FC/NES | 固定配置は先頭から再取得。マッパー方式は読み出し手順の初期化とバンク設定を再実行。同じモードの接続を使用 |
| GB/GBC | 各バンクのROMレジスター設定を再実行して先頭から取得。同じモードの接続を使用 |
| MD | 方式に応じたROMマッピング設定を再実行して先頭から取得。同じモードの接続を使用 |
| PCE | 各ブロックのアドレス指定と、必要な方式ではバンク設定を再実行。同じモードの接続を使用 |
| GBA | 04(0)・05・200ms待機、状態確認、完全な先頭2 KiBの受信とヘッダー一致を確認して先頭から取得 |
| SFC | 終了処理後に状態確認、初期化、安定したヘッダーと方式の一致を再確認。専用ROMマッピングも再設定して先頭から取得 |

GBA・SFCの2回目直前の不一致・不完全な応答・抜去・初期化失敗は保存せず停止する。SFCのヘッダー不正の限定再試行は識別時と最初の読み出し開始時だけに適用し、2回目直前には適用しない。

全機種をサービスの `SYSTEMS` に登録し、`poll` と `capture` を共通の入口から呼ぶ。ヘッダー中心の機種は `HeaderSystem` でDB読み込みと取り込みを共有し、NESは `NesSystem` で複数候補・自動判定グループ・書き込み直前の再識別を扱う。選択の検査は通信前に行い、取り込み中の例外では共通の処理で接続を閉じる。

保存処理はサービスの `_save_capture` に集約する。全機種で公開・競合回避・保存後の再照合を行い、成功してから選択中プロファイルを更新する。

| 層 | 内容 |
|---|---|
| 通信 | 応答ヘッダー、受信長、末尾の状態応答（機種の一致） |
| 独立2回読み | 全ROMを2回読み、バイト列が完全に一致すること |
| ヘッダー | 機種ごとのヘッダー・ロゴ・チェックサム・範囲 |
| 部分検証 | FCでは PRG、CHR、PRG+CHR の各SHA-1 |
| 全体ハッシュ | DBの全体SHA-1。SHA-256が収録されていれば併せて一致が必須 |
| 保存後 | 保存したファイルを再読込して再照合 |

- 容量の短縮にFF領域やミラーの推測を使わない。容量はDBの収録サイズごとの全体ハッシュで確定する。

## 保存

### ファイル名

- DBの正式名を安全なファイル名にして使う。拡張子は機種ごと：.nes（16バイトのiNESヘッダー付き）、.gb、.gbc、.gba、.md、.pce、.sgx、.sfc（コピーヘッダーなし）。
- 拡張子を除く名前はUTF-8で170バイトまでに切り詰める。ハッシュ付きの別名（`.verified-<SHA-256>`）を付けても、1つの名前が255バイトを超えないようにするため。同梱DBの最長のタイトルはこの上限に収まるので、既存の保存名は変わらない。
- MDは受信したバイト列をそのまま保存する。16ビット交換、SMDインターリーブ、512バイトヘッダーの付加は行わない。
- PCEは、データ順（受信順、またはバイトごとのビット反転）をDB照合で決め、正規化したデータを保存する。

### 一時ファイルからの公開

1. 保存先と同じディレクトリに、`.rfdump-<乱数>.tmp` を排他的に作る。
2. データを書き、flush と fsync を行う。
3. 既存ファイルを置換しない方法で、最終名へ公開する。
4. 一時ファイルを削除し、ディレクトリを同期する（環境によっては利用できないため、ベストエフォート）。
- 公開の方法：Windowsは os.rename（既存があれば失敗）。Linuxは renameat2 の RENAME_NOREPLACE。ライブラリーに関数がない32bit ARM（EABI）ではシステムコール番号382で直接呼ぶ。それも使えない場合はハードリンク方式を試し、対応できないストレージでは安全側に倒して失敗する。
- 古い一時ファイル（1時間超）は、保存のたびに掃除する。対象は自分の命名規則の一時ファイルだけ。
- 不完全な書き込みは一時名のまま残り、ROM名では公開されない。
- fsyncやディレクトリ同期は、すべてのSDカードで電源断に耐えることを保証しない。

### 競合時の扱い

| 状況 | 動作 |
|---|---|
| 同名・同内容の既存ファイルあり | 再利用（新規作成なし） |
| 同名・別内容の既存ファイルあり | 既存を移動・削除・上書きせず、`<元の名前>.verified-<SHA-256>.<拡張子>` で検証済みデータを保存 |
| 別名側にも同名の別内容あり | 保存を失敗として扱う |
- 画面には、既存ファイルをそのまま残した旨を表示する。
- 別名ファイルの再利用や起動のときも、名前に含まれるハッシュは信用せず、全体ハッシュを再計算して検証する。

### 既存ROMの探索

- 選択中の候補について、次の順に、DB全体ハッシュで検証できるものを探す。
  1. 保存先の正式名のファイル
  2. 保存先の `.verified-` 別名ファイル
- 検証結果は、パス・サイズ・更新時刻をキーにキャッシュする。ゲーム起動の直前はキャッシュを使わず再検証する。

## ゲーム起動（MiSTer）

1. 画面でGAME STARTを確認する。
2. 管理画面はリーダーを解放し、選択中のタイトルの保存済みROMを再検証する（ヘッダー・PRG・CHR・全体）。
3. ROMが保存先の外（互換保存先）にあれば、保存先へ検証済みコピーを保存する。
4. 機種のコア設定を読み、コアのRBFがSD上に存在することを確認する。
5. MGL（MiSTer Game Description）をアプリのruntimeフォルダーに一時ファイル経由で作る。内容は `rbf`（コア）と `file`（delay、type、index、ROMの絶対パス）。ファイル名は `<機種>_<raw SHA-1>_<ヘッダーハッシュ先頭8桁>.mgl`。
6. `/dev/MiSTer_cmd` に `load_core <MGLの絶対パス>` を1行、非ブロッキングで書く。FIFOでない、または受け手がいない場合はエラーとして画面に戻る。コマンドは制御文字を含まず1000バイト以下。
- コア設定の検証：rbf はSDルートからの相対パスで、拡張子 .rbf を付けない。絶対パス・`..`・バックスラッシュ・制御文字は不可。type は f、index は PCE が 0、その他は 1、delay は1〜30秒。
- ゲーム終了後の復帰はMiSTer側（Reboot）が担い、ゲームの終了を検出して管理画面を再表示する常駐機能は持たない。

## 取り込み時間の計測

- 取り込みの終了時（成功・既存同一・中止・エラー）に、直近1回分だけを `runtime/last_capture_metrics.json` へ記録する。書き込みに失敗してもROMの保存結果は変えない（記録は一時ファイル経由で置換し、失敗は握りつぶす）。
- 記録内容：

| 項目 | 内容 |
|---|---|
| version／scope | 形式の版（1）と範囲（capture_only） |
| outcome／error_type | saved、identical、cancelled、error と例外名 |
| elapsed_seconds | 取り込み開始から終了処理までの秒数（記録ファイルの書き込みは含まない） |
| phases | 画面へ通知した段階ごとの秒数と通信集計 |
| io | 転送路の read／write の回数、成功バイト数、例外数、所要秒数（Pythonから見た呼び出し全体で、ドライバー待ちを含む） |
| operation_seconds | 取り込み中に必要になったDB読み込み（load_*_database）、FCの直前候補確認（identify_nes）、保存関数（save_verified_rom）、保存後検証（verify_saved_file）の秒数 |
| system／transport／reader／rom_bytes | 機種、転送路のクラス名、build／product、成功時のROM本体サイズ（FCのヘッダー16バイトを除く） |
| recorded_utc／python／platform／machine | 記録時刻（UTC）と実行環境 |
| bundle_manifest_sha256 | 配布manifestのSHA-256（なければnull） |
- io と operation_seconds は phases・elapsed_seconds の内訳であり、合算すると二重計上になる。
- 計測は転送路の呼び出しを包むだけで、通信内容や呼び出し順序を変えない。受信したデータは保持しない。
- 取り込み時間の大半は転送路の読み書きが占めるため、計算部分の最適化より通信回数と転送量の削減が効く。
